# 服务路线

用于在本机、WSL2 或远程主机运行网站、API、守护进程和多组件服务。遵循项目官方说明，不把本文件当作安装百科。

## 选择运行方式

1. 确认目标环境、长期运行要求和是否需要公网。
2. 在官方支持的路径中选择依赖较少、稳定且便于维护的方式。
3. 官方提供受支持的镜像、持久化和更新路径时可选择 Docker/Compose；需要宿主机深度集成或容器化会变成非官方重设计时选择原生安装。
4. 只有两种以上路线都满足目标时才比较取舍。

目标为远程 Linux 或 VPS 时先运行：

```text
scripts/preflight.sh basic
```

只在已选路线需要时增加 `docker`、`ingress` 或 `web-stack`。根据实际结果报告适合部署、勉强可部署或不建议部署。

## 分阶段执行

命中记录分支时，按 `references/artifact-contracts.md` 判断并创建必要记录。每个阶段先说明目标、影响和撤销方式，再执行并验证：

```text
运行环境 -> 配置与秘密 -> 数据与持久化 -> 应用启动 -> 内部验证 -> 外部访问
```

根据项目删减阶段，不为简单服务制造空步骤。备份会被覆盖的配置，固定 Release、commit 或镜像 digest，并保护无关服务。

## Docker / Compose

启动前检查：

- Compose 配置能够解析，镜像引用能够从官方发布渠道或 registry 验证；
- 端口、网络、挂载路径、目录权限和秘密注入方式明确；
- 空 bind mount 不会遮蔽镜像预置配置、数据库或初始化文件；
- 数据卷、备份范围、迁移和首次管理员流程真实可用；
- 不会覆盖或停止无关容器和服务。

启动后检查容器状态、必要日志和本地应用响应。有状态服务执行一次无敏感数据的最小写入、读取，并在重启后复查持久化。

## 原生服务

确认运行账号、依赖版本、配置路径、数据目录、日志、启动方式和重启策略。长期运行优先使用项目支持的服务管理方式，并验证重启后能够恢复。

## 多组件项目

只为真实存在的组件列出作用、依赖、内部入口、公网入口和验证方式。先验证数据库、缓存等依赖，再验证 API，最后验证用户端和管理端的真实调用链。

## 验证

- 本地上游先于反向代理和公网入口验证；
- 使用项目文档、OpenAPI、CLI 帮助、源码路由或实际响应确定探针；
- 先确认状态码、字段和数据粒度，再编写断言；
- 区分应用故障和验证探针错误；
- 公网服务再验证域名、HTTPS、关键代理路径和现有站点健康。

完成标准：所选路线的进程或容器、应用响应、必要持久化和用户要求的访问方式均已验证；否则准确报告“部分成功”或“阻塞”。

## 失败处理

保留准确错误和基线状态，按文档/版本、镜像、架构、依赖、初始化、认证、网络、端口、存储、权限、运行时、验证探针或应用行为分类。未恢复到稳定状态时不要继续下一个阶段。
