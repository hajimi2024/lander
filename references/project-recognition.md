# 项目识别

## 可信来源顺序

按照以下顺序使用证据：

1. 仓库 README、Installation/Getting Started，以及 `AGENTS.md` 等仓库说明。
2. 上述文档引用的官方部署和配置文件。
3. 选择版本时需要的官方 Release 和迁移说明。
4. 兼容性不明确时由维护者回复的 Issue 或 Discussion。
5. 文档与实际行为冲突时的相关源码。
6. 第三方资料只作为辅助证据。

默认不要读取所有层级。

## 第一轮读取范围

读取 README 和安装说明。仅在文件存在且与识别有关时读取：

- `compose.yaml`、`docker-compose.yml` 或等价文件
- Dockerfile
- `.env.example`
- 包管理清单
- README 明确提到的服务或安装器定义

只有直接读取无法获得必要核心文件时，才使用临时克隆。临时克隆只用于分析：不安装依赖、不构建、不拉取镜像、不修改目标环境。分析后删除；除非用户随后将其选为正式工作目录。

## 项目分类

首先判断仓库属于：

- **可运行项目**：需要在目标设备上运行的应用、服务、守护进程、CLI、网站或开发工具。
- **可导入项目**：官方路径是安装或导入，而不是服务器部署的模板、浏览器扩展、MCP 服务/配置、Codex/Claude Skill、插件、库资源或其他制品。

然后识别官方主要方式。Dockerfile 或 Compose 文件只是证据，不是决定依据；只有官方文档推荐 Docker，或它明显是最简单且受支持的稳定路径时，才优先 Docker。

对于浏览器扩展、WordPress、MCP、Skill、插件、模板和 CLI，只按仓库证据路由到官方安装或导入说明，不编造详细的通用教程。

## 使用目标与开发目标

如果官方同时提供直接使用方式和开发者方式，先询问用户是直接使用项目，还是准备开发、修改源码或实时编译。

默认推荐满足当前目标且依赖最少、操作最简单、风险最低的官方路径。例如静态模板可以直接打开 `dist/index.html` 时，先推荐直接使用；只有用户明确选择开发时，才进入 `npm install`、`npm start` 或构建流程。

## 轻量资源判断

- 官方给出最低或推荐配置时，直接采用官方说明。
- 官方没有说明时，根据项目类型、服务数量、浏览器/数据库/AI 依赖和官方落地方式快速判断。
- 只报告轻量、中等或较重等简短经验级别，并说明主要原因。
- 初步判断时，不深入全部源码、不模拟构建、不计算所有依赖。

用户选择 VPS 后，用 `preflight.sh basic` 的当前资源余量结果替代初步估算，并判断为适合部署、勉强可部署或不建议部署。

## 第一轮回复

默认使用用户当前对话所使用的语言。不要跟随 README、仓库作者或官方文档的语言自动切换；命令、代码、路径、文件名、项目名称和标准技术术语保留原文。

简洁返回：

- 项目是做什么的
- 项目类型
- 官方推荐落地方式
- 主要依赖
- 轻量资源判断
- 初步建议
- 如果简单使用与开发流程并存，当前使用意图
- 当前决策节点必需的 1～3 个问题

到此停止。在用户确认继续前，不创建部署记录。

## 升级证据来源

只有出现以下情况时，才读取 Release、Issue、源码或第三方说明：

- 官方文件互相矛盾或缺少必要信息；
- 目标架构或版本兼容性不明确；
- 当前证据无法解释已经观察到的错误；
- 必须理解一键脚本生成配置的实际行为。
