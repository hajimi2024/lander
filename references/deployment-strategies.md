# 落地策略

保持策略选择精简。遵循具体仓库的官方说明，不要把本文件写成安装百科。

## 可运行与可导入

- **可运行项目**：选择软件在哪里、以何种方式运行，然后安装、配置、启动并验证。
- **可导入项目**：遵循官方导入或安装入口。不要仅因为仓库包含代码，就强行套用 Docker 或 VPS 流程。

根据仓库证据路由浏览器扩展、WordPress、MCP、Skill、插件、模板、库和 CLI。只有反复实际使用证明某一类型需要大量独立说明时，才考虑拆分专用模块。

## 方法选择

只在官方支持的方式中选择，并按以下顺序判断：

1. 先确认用户目标是直接使用，还是开发、修改源码或实时编译。
2. 在能满足当前目标的官方方式中，选择依赖最少、操作最简单、风险最低且稳定的路径。
3. 需要长期运行时，采用适合目标环境的官方生产建议。
4. 只有目标环境限制要求时，才采用有官方文档支持的替代方式。

如果简单使用路径已经满足目标，不要默认进入 `npm install`、`npm start`、构建或开发服务器流程。只有用户明确选择开发时，才采用开发者路径。

官方推荐或明确打包了受支持运行环境、数据持久化和更新路径时，选择 Docker/Compose。项目推荐原生安装、需要与宿主机集成，或容器化会变成不受支持的重新设计时，选择原生安装。

## 目标设备选择

- **本地电脑**：使用原生平台或受支持的本地容器运行时。除非用户明确要求发布到局域网或互联网，否则跳过 VPS 入口和证书工作。
- **WSL2**：按 Linux 环境处理，同时考虑 Windows 文件系统、端口、服务和重启边界。
- **VPS**：选择后，任何修改前先运行 `preflight.sh basic`。只有相应路线已启用时，才增加 `docker`、`ingress` 或 `web-stack` 模式。

## 通用执行原则

- 记录选定的 Release、tag、commit 或镜像标识。
- 只确认当前阶段需要的路径、凭据和设置。
- 备份会被覆盖的配置，并尽可能使用可恢复的目标环境覆盖配置。
- 将秘密信息排除在版本控制和输出之外。
- 明确数据持久化、所有权、重启行为和更新方式。
- 每次执行一个阶段，验证后再继续。

## 验证

按照实际采用的方式验证：

- 原生安装：可执行文件或服务状态、版本、日志，以及功能命令或健康响应。
- Docker：Compose 有效性、容器状态、健康检查/日志、端口绑定、挂载和已应用的资源限制。
- 可导入项目：目标应用成功识别，并完成一个最小功能检查。
- VPS 网络服务：先验证本地上游响应，再测试选定的外部访问方式。

## 失败处理

保留准确错误和未改变的基线状态。将问题归类为文档/版本、架构、依赖、身份验证、网络、端口归属、存储、权限、运行时或应用行为。只按分类需要查询 Release、Issue 或源码。不要掩盖失败并继续后续阶段。
